# Build plan — kafka-streams-risk-engine

Seven stages. **Every stage ends with a repo that runs, demos something, and could be pushed
public without embarrassment.** If you stop after stage 3 you still have a better Kafka project
than most of what is on GitHub.

Stack: Java 21, Spring Boot 3.3.5, Gradle 9.6 Kotlin DSL (matching
`kafka-wikimedia-stream-pipeline`), Confluent Kafka Streams + Avro + Schema Registry,
Testcontainers, Docker Compose.

**Progress: stages 0–3, 6 and 7 (evaluation) are done.** 42 tests pass, and each stage has been
verified against the live Docker stack, not only in `TopologyTestDriver`. Stages 3 and 6 were
verified with two instances. Stages 6 and 7 were pulled ahead of 4 and 5. Stage 7's
presentation items (GIFs, walkthrough page, deploy, CI) are still open.

---

## Stage 0 — Skeleton ✅

- Multi-module Gradle build: `risk-engine`, `traffic-generator`, `common-avro`
- `docker-compose.yml`: Kafka in KRaft mode (single broker), Schema Registry, AKHQ or
  kafka-ui for topic inspection
- Avro schemas in `common-avro/src/main/avro/`, generated by the `gradle-avro-plugin`
- Topic creation via an init container, not by hand
- Spring Boot app that starts a Kafka Streams instance with a no-op topology and exposes
  `/actuator/health` including Streams state

**Done when:** `docker compose up` gives a green health check and kafka-ui shows the topics.

**Watch for:** the Avro plugin and Gradle's configuration cache do not always get along; if
builds are slow, that is the first thing to check.

## Stage 1 — Enrichment ✅

- `cards`, `customers`, `merchants` as Avro records, seeded into Postgres by a Flyway migration
- For now, publish reference data with a simple producer — **Debezium comes in stage 5**, so
  this stage is not blocked on Connect working
- `cards ⋈ customers` FK join → `cardProfiles` KTable
- `merchants` as GlobalKTable
- `transactions ⋈ cardProfiles ⋈ merchants` → enriched stream, written to a temp topic
- Traffic generator: `baseline` scenario only
- Sparkov CSV loader — parse, map fields, produce to `payments.transactions.v1`. Small, and it
  front-loads the field mapping. See [DATA.md](DATA.md)

**Done when:** an enriched transaction in kafka-ui carries the card limit, the customer risk
tier, and the merchant MCC.

**Watch for:** this is where you will hit the classic "join produces nothing" wall. Almost
always co-partitioning: the stream and the table must have the same number of partitions and
the same key. Write down what actually went wrong — it becomes a good README footnote.

## Stage 2 — The decision path ✅

Built as planned, plus: a left join so unknown cards are reviewed rather than dropped, an
event-time `TimestampExtractor` (brought forward from stage 4), `CARD_NOT_ACTIVE`,
`CARD_TESTING` and `MERCHANT_RISK` rules, and state updates that depend on the verdict.

- `RiskEvaluator` as a Processor API node
- Stores: `velocity-store` (WindowStore, 1 h retention), `spend-store`, `geo-store`
- Rules R1 velocity, R2 daily limit, R3 impossible travel
- Score bands, `reasons[]`, write `Decision` to `payments.decisions.v1`
- `TopologyTestDriver` tests for all three rules
- Punctuator for geo-store eviction, tested with `advanceWallClockTime()`
- Traffic generator: `card-testing`, `impossible-travel`, `limit-breach` scenarios

**Done when:** running the `impossible-travel` scenario produces a `DECLINE` with reason
`GEO_VELOCITY` and the tests prove it without a broker.

**This is the core of the project.** Stages 3–7 are amplifiers. Do not rush this one.

## Stage 3 — Interactive Queries and the dashboard ✅

Built as planned. The query assembles all five card stores (profile, spend, location,
velocity, last decision), not just the profile. It queries only the one partition that holds
the card (`StoreQueryParameters.withPartition`). The "second instance behind nginx" is
replaced by running a second `bootRun`, which shows the same routing with less setup. The
dashboard's feed is a plain consumer assigned every partition, so each instance shows all
traffic.

Measured in live verification: routing correct in both directions; killing one of two
instances gave `503 owner unreachable` for ~35 s, then the survivor served the same data
restored from changelogs. That 35 s is the baseline for the stage 6 standby-replica demo.

- Materialise `CardRiskProfile` into a queryable store
- `GET /risk/cards/{cardId}` reading the local store
- Cross-instance routing: `queryMetadataForKey` → HTTP proxy to the owning host, driven by
  `application.server`
- `GET /risk/instances` exposing partition ownership
- Second app instance in compose, nginx in front
- Dashboard: one HTML page, SSE feed of decisions, per-rule counters, partition-ownership panel

**Done when:** you can query a card whose partition lives on the *other* instance and get the
right answer, and the dashboard shows decisions arriving live.

**This is the "Kafka is not a message queue" moment.** Record the GIF here.

## Stage 4 — Analytics path and suppression

- `decisions.selectKey(merchantId).repartition()`
- 5-minute tumbling window with 30 s grace, decline rate per merchant
- `suppress(untilWindowCloses)` → `risk.merchant-stats.v1`
- `GET /risk/merchants/{id}/stats` over the windowed store
- Custom `TimestampExtractor` reading `eventTime`
- A test that feeds a late record and asserts it lands in the right window

**Done when:** the merchant-stats topic gets exactly one record per merchant per closed window,
not a stream of intermediate updates.

## Stage 5 — CDC

- Debezium Postgres connector in compose, with the connector registered by an init container
  rather than a curl command in the README
- Reference data now flows Postgres → Debezium → compacted topics → KTables
- Demo: `UPDATE cards SET daily_limit_minor = ... WHERE ...` in Postgres, and watch the next
  transaction for that card get evaluated against the new limit within seconds

**Done when:** that demo works end to end with nothing restarted.

**Watch for:** Debezium emits envelopes with before/after; you need an unwrap SMT
(`ExtractNewRecordState`) plus tombstone handling for deletes to make compaction behave.

## Stage 6 — Production hardening ✅ (except Grafana)

Built: exactly-once v2, a synchronous DLQ with provenance headers, standby replicas with
automatic stale-read fallback in the query routing, a `deviceFingerprint` schema evolution
verified against an engine running the old code, Prometheus metrics, and a `latency` probe in
the traffic generator. Not built: the Prometheus + Grafana compose services and dashboard.
Also not built: a `ProductionExceptionHandler`. The default already fails on every
production error, which is the intended behaviour, so there was nothing to add.

Measured live, with the numbers in the README: standby failover served reads 0.4 s after a
hard kill, against a ~35 s outage without standbys. EOS against ALOS latency showed no EOS
penalty at 20 tx/s. The DLQ caught a raw-JSON poison pill with full provenance and the engine
kept running.

### Original plan

- `exactly_once_v2` on the decision path, with the latency cost measured and written down
- DLQ: custom `DeserializationExceptionHandler`, failure metadata in headers
- `ProductionExceptionHandler` and `StreamsUncaughtExceptionHandler`
- `num.standby.replicas=1`, `enableStaleStores()` behind a query parameter
- **Failover demo**: kill an instance under load, poll the API, show the difference with and
  without standbys
- Schema evolution: add an optional `deviceFingerprint` field to the transaction schema, prove
  the running consumer keeps working, test it
- Micrometer metrics → Prometheus → a Grafana dashboard in compose (lag, state store size,
  process latency, punctuation rate)

**Done when:** you can kill an instance during a demo and the API stays up.

## Sequencing notes

- **Stages 1–3 are the minimum viable portfolio piece.** Push public at the end of stage 3.
  Everything after that is upside, and shipping early beats a perfect private repo.
- Stage 5 (CDC) is the most likely to eat a weekend on infrastructure rather than on Kafka
  Streams. It is deliberately late so it cannot block the parts that actually demonstrate the
  skill.
- Stage 6's failover demo is the highest value-per-hour item in the whole plan. If time gets
  short, do that before the rest of stage 6.
- Keep a `docs/NOTES.md` of things that broke and why. Turn the three best ones into a README
  section called "Things that bit me". Interviewers ask about exactly this, and having written
  answers means you are not reconstructing them under pressure.
